\section{Three paths define the operated system}

The \textbf{training path} validates a data snapshot, constructs split and
features, fits candidates, evaluates them, and promotes an immutable artifact.
The \textbf{prediction path} validates a request or batch, applies the exact
feature transformation and approved artifact, and records output context. The
\textbf{feedback path} joins predictions to outcomes after the target horizon
and produces evidence for continuation, investigation, rollback, or retraining.

Each arrow requires identity, schema, version, time, error, retry, access, and
retention semantics. The paths may run at different cadences and on different
infrastructure, but their contracts must agree.

\section{A model artifact is more than parameters}

An approved artifact binds together a feature schema and order, fitted
transformations, model state, class or output semantics, supported runtime,
training-data and code references, evaluation report, and model card. A registry
records lifecycle state such as candidate, approved, superseded, or withdrawn.

Never load arbitrary serialized objects from untrusted sources. Many Python
serialization formats can execute code. Control provenance, integrity, access,
and runtime compatibility. Prefer constrained formats when they represent the
needed operations faithfully.

\section{Offline and online features must agree}

Training-serving skew occurs when feature computation differs between historical
training and live prediction. Causes include time-zone handling, category
vocabularies, window boundaries, late data, default values, code versions, and
units. Reuse package code where possible, and test representative raw records
through both paths.

Point-in-time correctness is essential: a historical feature must use only
information available at its historical prediction time. Recomputing it from a
current database can accidentally include future corrections or outcomes.

\section{Prediction interfaces fail explicitly}

Batch inference favors throughput, snapshot lineage, restartable partitions,
and idempotent outputs. Online inference adds latency, concurrency, admission
control, timeout, and availability responsibilities. Both validate schemas,
bound resources, record artifact identity, and reject incompatible requests.

The interface should define behavior for missing, unknown, infinite, or out-of-
support inputs. Abstention or routing to human review can be safer than a forced
prediction. Error responses must not leak secrets or silently substitute a
different model.

\section{Operating evidence is part of the model contract}
\label{sec:production-observability}

Offline evaluation estimates behavior under a stated sampling and measurement
process. Release changes the question. The team must now determine what code,
data, model, policy, and dependencies actually served clients; whether the
system met its operational objectives; and whether later outcomes support the
original predictive claim. Source code alone cannot answer those questions.

Four terms should be separated. \textbf{Telemetry} is evidence emitted by a
running system. \textbf{Monitoring} repeatedly checks selected evidence and
conditions. \textbf{Observability} is the property that permits investigators
to infer useful internal behavior from available evidence. \textbf{Model
monitoring} concerns feature validity, populations, scores, decisions, slices,
and outcomes for a learned component. Installing a dashboard product does not
make an uninstrumented or semantically ambiguous system observable.

The first design question is not ``What can this tool display?'' It is ``Which
failure must an operator distinguish, and what evidence would separate its
competing causes?'' Instrumentation follows the diagnostic question.

\section{Failure layers require different evidence}

An HTTP 200 response proves that an endpoint produced a response under its
transport contract. It does not prove that the request used the intended units,
feature meanings, model, decision policy, or population. Conversely, an
accurate model is not useful when its service is unavailable. Reliability
therefore has several causal layers.

The layers interact. A sensor firmware change can look like population shift; a
unit conversion defect can look like model decay; a failed outcome join can
make quality appear stable because the hardest cases disappear. An alert should
therefore initiate diagnosis, not name a cause prematurely.

\section{Logs, metrics, and traces answer different questions}

A \textbf{structured log} records one discrete event as named fields: timestamp,
event type, severity, request or prediction identifier, model and release
versions, and approved diagnostic context. It should not serialize arbitrary
arguments or complete feature vectors. Logs otherwise become an ungoverned copy
of sensitive inputs, credentials, or proprietary data. Field policy, access,
retention, and deletion are part of logging design.

A \textbf{metric} is a numeric time series. Request count, error count, duration,
queue depth, rejected-input count, score histogram, and joined-outcome count can
be aggregated over time and across replicas. Labels define groups, so their
value sets must remain bounded. Route, status class, risk band, and deployed
model version may be controlled labels. Request IDs, prediction IDs, raw error
messages, users, and timestamps are not: they can create an effectively
unbounded number of time series. This \textbf{cardinality} failure can exhaust a
monitoring system during the incident when it is most needed.

A \textbf{trace} follows one unit of work through nested spans. An HTTP request
may contain spans for schema transformation, feature lookup, model execution,
database write, and downstream calls. Metrics establish scope; a sampled trace
localizes representative work; logs explain selected events. A request ID is an
application correlation identifier, while a trace ID belongs to the tracing
system. Recording both can connect evidence without using either as a metric
label.

\textbf{Diagnostic order.} Begin with the client-visible symptom. Use metrics to
determine scope, traces to locate work, and logs to inspect relevant events.
Scrolling through all logs is not an investigation strategy, and absence of
error logs is not proof of correctness.

The common service summary called RED records request \textbf{rate},
\textbf{errors}, and \textbf{duration}. Saturation and dependency health add
capacity context. These signals remain necessary for a model service, but they
cannot establish feature meaning or predictive quality.

\section{Model monitoring needs a feedback path}

Operational monitoring covers rate, latency, errors, saturation, artifact load,
and dependency health. Data-quality monitoring covers schema, missingness,
range, category, freshness, units, and joins. Distribution monitoring compares
feature, score, and decision summaries with explicit reference windows.

Covariate shift means the distribution of $X$ changes. Prior shift changes
class prevalence. Concept shift changes the relationship between $X$ and $Y$.
Unlabeled inputs can reveal aspects of the first and sometimes the second; they
cannot by themselves measure predictive error or identify the third. A
prediction record therefore needs a stable join key, prediction time, target
horizon, score or action, model and policy identity, and lawful retention. When
the outcome arrives, the feedback path validates and joins it to the original
prediction rather than recomputing history from mutable current data.

Report quality estimates with their denominators, time windows, and slice
definitions. A Brier score computed from eight convenient outcomes is not
equivalent evidence to one computed from a representative sample of eight
thousand. Monitor slices defined before release and investigate emerging slices
carefully; repeated searching can turn random variation into an apparent
incident.

There are three important clocks: request time, outcome-availability time, and
monitor-computation time. A system can detect schema rejection immediately,
score shift after a monitoring window, and outcome degradation only after the
target horizon. Alert policy must respect these information delays.

\begin{misconceptionbox}
\textbf{Misconception:} feature drift means the model must be retrained.

\textbf{Correction:} drift is evidence to investigate. A producer change,
failed transformation, selection effect, or real population change may produce
the same summary. Retraining can preserve the defect, learn from corrupted
labels, or degrade important groups. Action depends on outcomes, cause,
severity, and the validated response policy.
\end{misconceptionbox}

\section{Alerts connect objectives to owned action}

A \textbf{service-level indicator} (SLI) is a measured quantity such as the
fraction of eligible prediction requests completed successfully within 250 ms.
A \textbf{service-level objective} (SLO) states a target over a window, for
example at least 99.5\% over 28 days. The objective should reflect a client
outcome and exclude only cases justified by the contract.

An alert is useful when it detects a meaningful symptom early enough for an
owner to act. Every alert needs a condition, evaluation window, urgency, owner,
runbook, evidence links, duplicate suppression, and recovery condition. Page on
sustained user impact or rapid consumption of an error budget, not every log
line. Model-quality alerts often require longer windows, minimum sample sizes,
and human review because their estimates are noisy and delayed.

A dashboard without a response policy is visualization, not operational
control. A runbook should state safe first checks, authority limits, reversible
mitigations, escalation contacts, and verification. It should never instruct an
operator to delete evidence, expose data, or retrain reflexively.

\section{Incident diagnosis is disciplined inference}

An incident response can be organized as a sequence of falsifiable decisions:

\begin{enumerate}
  \item state the exact client symptom and time interval;
  \item preserve release, model, data, configuration, and deployment identity;
  \item form at least two competing hypotheses;
  \item use aggregate metrics to establish scope;
  \item select a representative trace to localize work;
  \item inspect correlated structured events rather than the entire log stream;
  \item examine feature, score, decision, slice, and outcome evidence as needed;
  \item apply the safest reversible mitigation within the responder's authority;
  \item repeat the original client action and verify recovery; and
  \item record the timeline, cause, impact, repair, and preventive controls.
\end{enumerate}

Restarting first can destroy diagnostic state. Changing several components at
once prevents causal attribution. A useful post-incident review separates facts
known at the time from later conclusions and assigns follow-up actions with
owners and verifiable completion criteria.

\begin{workedexample}{one application, two very different incidents}
The repository's production monitoring laboratory operates a FastAPI battery-
risk service backed by package modules and SQLite prediction lineage. A traffic
script acts as the client. Prometheus stores metrics, Loki stores structured
events, Tempo stores OpenTelemetry traces, and Grafana presents a provisioned
dashboard. No notebook is part of the runtime.

First, an instructor introduces delay in the feature-contract operation. The
request-rate panel remains stable, the error ratio remains near zero, and the
95th-percentile latency rises. A representative trace assigns most of the
duration to \code{feature\_contract.apply}. The team restores the healthy
configuration and verifies the original latency symptom with new traffic.

Second, the service remains fast and returns HTTP 200, but the temperature
transformation assumes Fahrenheit for inputs contracted as Celsius. Service
health remains green while score and risk-band distributions shift. A
\code{prediction\_completed} event records the model and release identities and
the approved unit-assumption field; the correlated transformation span confirms
where semantics changed. Retraining would not repair this defect. The correct
response restores the feature contract, tests the unit boundary, and evaluates
the affected predictions and later outcomes.

The exercise makes a central distinction observable: software availability and
model validity are related operational responsibilities, not the same claim.
\end{workedexample}

\section{Retraining is a release, not a reflex}

A retraining trigger begins a candidate-building workflow. The candidate must
pass data validation, tests, evaluation, subgroup and resource gates, and
approval. Automatic promotion is appropriate only when those gates and rollback
controls match the consequence of failure.

Rollback requires a previously known artifact, compatible feature interface,
and a procedure tested before the incident. Some shifts make rollback
insufficient because the old artifact faces the same new population. A safe
fallback may be a baseline, abstention, reduced scope, or human review.

\begin{professionalbox}
Separate the decision to recompute a candidate from the decision to release it.
Schedule-driven retraining is an opportunity to evaluate new evidence, not a
guarantee that the newest artifact is better.
\end{professionalbox}

\section{The release dossier}

A defensible release records the prediction contract, data and feature lineage,
split specification, candidate search, final evaluation, known limitations,
model and policy versions, security review, test evidence, monitoring plan,
owner, rollback plan, and expiration or review date. CI verifies reproducible
software properties; human review owns scientific and operational judgment that
cannot be reduced to one test.

\begin{workedexample}{an incident closes the evidence loop}
After release, the degradation service remains fast and error-free, but a new
batch produces higher scores and more out-of-support warnings. Outcomes will not
arrive for 100 cycles. The runbook narrows automated use and routes affected
cells to review rather than immediately retraining.

Investigation finds a sensor firmware change that altered one summary feature.
The team reconstructs the feature with point-in-time data, evaluates both the
approved artifact and a candidate on the corrected representation, and records
the incident. A compatibility adapter restores the defined unit; the model is
not changed. Operational evidence prevented a data-interface defect from being
misdiagnosed as concept drift.
\end{workedexample}

\section{Exercises}
\begin{enumerate}
  \item Draw training, prediction, and feedback paths for batch inference. Mark
  every durable artifact and join key.
  \item Specify a feature-parity test involving time windows, late records,
  unknown categories, and units.
  \item Design monitoring that distinguishes service failure, input shift, score
  shift, calibration change, and outcome degradation.
  \item Write a rollback rehearsal and explain one shift for which rollback
  would not restore acceptable behavior.
\end{enumerate}

\begin{chapterreview}
A reliable supervised-learning system joins three paths. Training creates and
promotes versioned evidence; prediction applies an approved artifact through a
validated interface; feedback connects outputs to delayed outcomes. Monitoring
must cover operations, data, scores, slices, and eventual performance. Drift
prompts investigation, while retraining and rollback remain governed releases.
\end{chapterreview}
